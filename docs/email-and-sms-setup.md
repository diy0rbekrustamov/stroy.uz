# Почта, SMS и вход продавца

## Как открыть кабинет продавца

1. Запустить frontend: `npm run dev`, а в другом терминале локальный API: `npm run api:local`.
2. Открыть `/register`, выбрать «Продавец», заполнить форму и зарегистрироваться. Если аккаунт уже создан — войти через `/login`.
3. Перейти по «Кабинет продавца» или открыть `/seller`. Для существующего покупателя доступна форма «Стать продавцом» с названием магазина; это тот же аккаунт, история покупок сохраняется.
4. Создать товар, услугу или технику. Черновик доступен только владельцу. После публикации объявление появляется в соответствующем каталоге.

Если API недоступен, кабинет показывает ошибку и повторную загрузку. Демо-каталог может отображаться без API, но настоящая регистрация и сохранение объявлений требуют сервера.

## Демо-карточки перед запуском

Сейчас в разработке примеры сохранены; реальные опубликованные объявления добавляются перед ними. Примеры не являются объявлениями продавцов в БД, их нельзя оформить как настоящий заказ.

Перед запуском установить `VITE_DEMO_CATALOG=false` в `.env`/переменных окружения сборки и заново собрать frontend (`npm run build`). В production демо по умолчанию выключено; `VITE_DEMO_CATALOG=true` явно включает его для демонстрационного стенда. Переменная VITE доступна браузеру: хранить в ней секреты нельзя.

## Что уже реализовано для восстановления

Сейчас используется **ссылка на email**, не шестизначный код. Сервер хранит хеш одноразового токена, срок действия 30 минут. После смены пароля токены и активные сессии пользователя удаляются. Запрос ограничен по частоте. Без SMTP интерфейс показывает, что почтовый сервис не настроен. Реальная доставка на почту пока не проверялась.

Это восстановление доступа, а не подтверждение email при регистрации. Автоматического подтверждения владения номером сейчас тоже нет.

## Подключение email через SMTP

Нужны аккаунт почтового провайдера, домен команды и доступ к его DNS. Например, Resend принимает отправку через SMTP и требует подтверждённый домен: [SMTP](https://resend.com/docs/send-with-smtp), [верификация домена](https://resend.com/docs/dashboard/domains/introduction).

Порядок для куратора:

1. Создать аккаунт сервиса, добавить принадлежащий команде домен/поддомен и указанные провайдером DNS-записи. Дождаться подтверждения. Домен STROY UZ в примерах не означает, что он уже принадлежит команде.
2. Создать ключ только для отправки писем. На сервере внести значения в `.env` или хранилище секретов. Пример для Resend:

```dotenv
SMTP_HOST=smtp.resend.com
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=resend
SMTP_PASSWORD=REPLACE_WITH_PRIVATE_SENDING_KEY
SMTP_FROM="STROY UZ <no-reply@your-verified-domain.example>"
APP_ORIGIN=https://your-site.example
```

3. Заменить домены `.example` настоящими адресами, проверить HTTPS и перезапустить API. На сервере также необходим PostgreSQL через `DATABASE_URL`; встроенная локальная БД не подходит для production.
4. На тестовом аккаунте команды запросить восстановление и проверить доставку, папку «Спам», срок ссылки и отказ при повторном использовании. Письма отправлять только на согласованные тестовые адреса.
5. Настроить мониторинг отказов доставки. Сообщение пользователю не должно раскрывать наличие конкретного аккаунта. Не записывать токены и ключи в логи.

В коде уже используется Nodemailer в `server/index.js`; новый SDK для такого SMTP не нужен. Для другого SMTP-провайдера заменить настройки по его официальной документации. Не отключать проверку сертификатов.

## Как подключить SMS-коды

Нужен SMS-провайдер с поддержкой нужных номеров Узбекистана, договорённостями по отправителю/шаблонам и пополненным балансом. Один из примеров API: [официальная документация USMS](https://api.usms.uz/). Выбор и условия подключения согласовать с куратором; аккаунты и оплачиваемые услуги сейчас не создавались.

Безопасная последовательность реализации:

1. Подключить серверный адаптер выбранного провайдера. Ключ хранить только на сервере, без префикса VITE. Браузер обращается к нашему API, а не напрямую к SMS-сервису.
2. Сначала подтвердить владение телефоном: нормализованный `+998…`, привязка к пользователю, подтверждённая уникальность номера и отдельное поле времени подтверждения. Сейчас телефон — контактное поле, а не доказанный способ восстановления.
3. Выдавать случайный одноразовый код, например 6 цифр, с коротким TTL (ориентир 5 минут), хранить защищённое значение с серверным секретом. Обычный SHA-256 от шестизначного кода без секрета недостаточен из-за малого пространства перебора.
4. Ограничить попытки проверки и отправку по номеру, аккаунту и IP; добавить паузу повторной отправки и общий лимит расходов. Повторная отправка не должна обходить лимит попыток.
5. После успешной проверки выдать короткоживущий одноразовый токен смены пароля; не возвращать существующий пароль. Привязать запрос к назначению «восстановление», чтобы код подтверждения номера нельзя было применить для смены пароля.
6. После смены пароля погасить код/токен и сессии. Предусмотреть восстановление при потере номера и уведомление об изменении привязанного телефона.

SMS-восстановление и подтверждение email при регистрации **ещё не реализованы**. Текущие эндпоинты принимают email и ссылку-токен; добавлять туда просто непроверенный номер нельзя. Тарифы и сроки доставки провайдера не измерялись.

Ни пароли от почты, ни API-ключи не отправлять в чат, GitHub или фронтенд. Их вводит куратор в окружение сервера.
